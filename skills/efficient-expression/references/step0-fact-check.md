# Step 0：事实核验与补齐协议（Fact-Check & Augmentation）

在进入表达构建前，先评估事实要素的**完整度（Completeness）**与**可信度（Authenticity）**。

这一步存在的理由很直接：三层 SOP 再漂亮，输入是模糊的，输出就只是把模糊包装得像结论。别人一旦追问细节，整段表达瞬间失去可信度。所以宁可在这里卡一次，也不要带着空洞往下走。

## 1. 事实评估标准（Fact-Check Standard）

逐条自检输入是否满足：

- **无模糊代词：** 没有“很多人”“可能”“很快”“大幅提升”这类不确定表述，取而代之的是具体数字、比例或明确边界。
- **归因链条完整：** 现象背后有可追溯的原因或数据支撑（“因为 X 指标从 1.2s 涨到 3.5s”而不是“因为系统很卡”）。
- **边界清晰：** 清楚知道问题的影响范围与对象（影响了多少用户、哪个区域、哪个版本、持续多久）。
- **时间锚点明确：** 说的“最近”“上周”有具体日期或统计周期。

四项里缺任意一项，且该缺失会改变读者的判断或决策，就必须补齐。只是修辞上的模糊（口语化的“差不多”）不影响，不必过度追问。

## 2. 补齐路由机制（Augmentation Routing）

判断缺失信息的**归属**决定走哪条路：公域知识可以自己去查，私域背景只有用户知道。

```text
                ┌─────────────────────────┐
                │ 事实缺失 / 信息模糊校验  │
                └────────────┬────────────┘
                             │
             ┌───────────────┴───────────────┐
             ▼                               ▼
   【公域知识 Public Knowledge】     【私域 / 内部背景 Private Context】
   技术原理、行业数据、公开法规、      项目进度、内部冲突、公司业务数据、
   外部竞品、概念定义                 团队分工、个人真实诉求
             │                               │
             ▼                               ▼
   【模式 A：Deep Research】          【模式 B：HITL 追问】
   自动调用 web search / web fetch     向用户提出 1–3 个结构化问题，
   检索并整理客观事实，标注来源，       等待回答补齐后再继续。不要边问
   补齐后继续。                        边猜、不要把猜测写进输出。
```

### 模式 A：Deep Research（公域知识自动补齐）

- **触发条件：** 缺少通用技术细节、行业标杆数据、公开法规或概念解释。
- **动作：** 调用宿主的 web search / web fetch 搜集 2–3 个权威数据点，在正文中以“来源 + 数据”的形式落地。
- **如果检索不可用：** 不要凭记忆编造数据。降级为模式 B，请用户提供数据，或明确标注该结论“待补数据”，不要给出看似精确的假数字。

### 模式 B：HITL — Human In The Loop（私域知识主动追问）

- **触发条件：** 缺少公司内部背景、项目具体指标、团队分工或个人真实诉求。
- **动作：** 中断生成，提出**简洁、定量、可一次回答完**的追问清单，**不超过 3 个问题**。超过 3 个会让用户放弃回答。

追问的质量决定补齐后的表达质量：问“情况怎么样”等于没问；问“影响时长和影响用户数分别是多少”，用户一句话就能答，且答案能直接进入 PROACT 的对比表。

#### HITL 追问模板样例

> 为了帮你生成最精准的汇报，我需要向你确认 2 个内部细节：
>
> 1. 这次服务器宕机具体的**影响时长**和**影响用户数**是多少？
> 2. 团队目前采取的临时方案，**预计还需要多长时间**彻底修复？

追问时顺带说明“为什么要问”，用户更容易给出你想要粒度的答案——例如“因为汇报里要放进方案对比表，需要具体耗时”。
