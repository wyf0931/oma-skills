# 案例 6：09-22 数据库连接池耗尽故障复盘

- **场景分类：** 故障汇报 / 事故复盘（Postmortem）/ 向上通告
- **受众定位：** 部门高管（只看第一段）+ 全体技术团队与运营团队（要看根因和动作）。同一份输出要同时满足两种精力预算。
- **动态 SOP 路径：**
  - **Step 0：** 事实完整（日志、监控数据、排查时间线齐备）。
  - **Step 1：** **5W1H + Metric-Variance**（还原影响范围与指标异常）
  - **Step 2：** **SCQA 压缩形态**（S 背景 → C 故障 → Q 根因 → A 止损与改进）
  - **Step 3：** **BLUF 强制前置**（第一句给级别、影响、恢复状态）+ **Data-In-Context** + **无责归因**

---

### 最终渲染输出（Rendered Output）

**【故障摘要（BLUF）】**
本次事故级别为 **P2**。故障已于 **14:35 完全恢复**。影响时长 **25 分钟**，期间约 **3.5%** 的线上 API 请求返回 500，影响约 **1.2 万名**下单用户，**未造成订单数据丢失**。

---

**【故障过程与影响（5W1H & Metric-Variance）】**

- **When：** 2026-09-22 14:10 – 14:35（持续 25 分钟）
- **What：** 订单服务数据库连接池耗尽，接口 RT 从基线 180ms 瞬间飙升至 10s+。
- **Why（根因）：** 大促 Push 带来的瞬时流量达到平时基线的 8 倍，而接入层缺少限流熔断、连接池容量未与营销活动联动。**这是机制缺口，不是某位同学的失误。**
- **How（止损）：** 紧急扩容数据库连接池，并开启 API 接入层限流熔断，14:35 系统指标恢复正常。

**【改进措施（Preventive Actions）】**

1. **架构优化：** 完成订单服务的 Redis 缓存层改造，阻断 80% 直连 DB 的读流量（负责人：张三，9/25 前）。
2. **协同机制：** 大促 Push 推送前必须提前 2 小时通知运维团队进行预热，并纳入发布检查单（负责人：李四，即刻生效）。

---

### 本例的可复用点

- **BLUF 会物理前置：** 这份输出里 BLUF 排在 SCQA 之前，是刻意的——Step 3 的结论先行会覆盖 Step 2 骨架的开头。加工顺序是 1→2→3，排版顺序由受众的精力预算决定（高管只读第一段）。
- **无责归因（blameless）：** 根因写到“接入层缺少限流熔断”就停住，不再指向“运营团队没通知”。指向人，下一次事故就没人敢第一时间上报，损失会更大。改进措施里用“纳入发布检查单”这种机制动作去承接，而不是追责。
- **改进措施必须带负责人与截止时间：** 不带的话只是感想。高管判断复盘是否可信，看的就是有没有可验证的收口动作。
- **数字带锚点：** “RT 10s+”没有意义，“从基线 180ms 飙升至 10s+”（约 55 倍）才让读者知道量级。
- **同一份输出服务两类受众：** BLUF 段给高管，5W1H + 改进措施给执行团队，中间无需分叉成两份文档。
