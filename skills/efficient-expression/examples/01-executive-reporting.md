# 案例 1：向 CTO 汇报 Agent 框架自研选型

- **场景分类：** 高管汇报 / 技术方案选型
- **动态 SOP 路径：**
  - **Step 0：** 触发 HITL 补齐了团队当前 QPS 与预算约束（原始诉求里只说“框架卡”）。
  - **Step 1：** **IPO 框架**（清洗技术吞吐与资源消耗事实）
  - **Step 2：** **PROACT 框架**（做决策方案对比）
  - **Step 3：** **BLUF + KISS**（结论先行，保留专业术语）

---

### 最终渲染输出（Rendered Output）

**【结论与请求】**
**建议启动轻量级 Agent 调度引擎自研（方案 A）。** 预计投入 2 名工程师研发 3 周，可将系统高并发 P99 延迟从 1.2s 降低至 250ms，单机 QPS 提升 4 倍，满足 Q4 业务冲刺要求。

---

**【决策权衡对比（PROACT）】**

为解决开源框架（LangChain / Haystack）在高并发下的内存泄漏与延迟问题，我们评估了三种方案：

| 评估维度 | 方案 A：基于 Rust 核心自研 | 方案 B：基于 Python 框架二次改造 | 方案 C：采购商业云服务 |
| :--- | :--- | :--- | :--- |
| **P99 响应延迟** | **250 ms**（达标） | 850 ms（偏高） | 300 ms（达标） |
| **单机并发上限（QPS）** | **3,500** | 800 | N/A（按量计费） |
| **研发与算力成本** | 2 人 / 3 周；硬件成本 -60% | 1 人 / 1 周；硬件成本无变化 | API 调用费约 $1.2 万 / 月 |
| **主要风险** | 前期有一定代码维护门槛 | 性能瓶颈在半年后会再次暴露 | 数据存在隐私合规风险 |

**【下一步计划】**
若同意方案 A，我们将在本周五前完成原型验证（PoC），并提交详细的架构设计文档。

---

### 本例的可复用点

- HITL 只问了 2 个问题（当前 QPS、预算约束），但这两个数字直接决定了对比表能否成立。
- 对比表给自己方案也如实列了风险（维护门槛），这是高管愿意采信的前提。
- 结论段同时给了“要什么资源”和“换来什么指标”，决策者不需要读第二段就能拍板。
