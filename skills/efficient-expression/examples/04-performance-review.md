# 案例 4：核心项目“数据采集引擎重构”绩效复盘

- **场景分类：** 绩效评估 / 晋升答辩 / 项目复盘
- **受众定位：** 直属上级 / 晋升评审委员会（不关心你有多努力，只判断你的判断力与贡献边界；精力预算中等）
- **动态 SOP 路径：**
  - **Step 0：** 事实完整（项目周期、个人动作、业务产出齐备），无需补齐。
  - **Step 1：** **Metric-Variance**（先算清基线与实际偏差）
  - **Step 2：** **STAR**（证明个人行为闭环）
  - **Step 3：** **Data-In-Context**（每个数字都带锚点）

---

### 最终渲染输出（Rendered Output）

**【S / T — 情境与任务】**
Q3 随海外电商业务拓展，爬虫系统面对的抓取量剧增 5 倍，旧版 Python 架构频繁触发 IP 封禁且耗时过长，直接影响 Marketplace Insights 的数据时效性。我作为项目 Leader，目标是在 Q3 内把日均解析商品数提升至 40 万以上，并把单位抓取成本压回 Q2 水平。

**【A — 个人行动】**
1. **架构重构：** 引入异步无头浏览器集群与自适应 IP 代理池，重写底层调度逻辑。
2. **算法优化：** 设计多级 KV Cache 机制，对高频商品页实现增量更新而非全量抓取。

**【R — 结果（Data-In-Context）】**
1. **抓取吞吐量：** 日均解析商品数从 20 万（Q2 基线）提升至 150 万，增长 650%，是部门目标（+200%）的 3.25 倍。
2. **成本控制：** 单位数据抓取的 IP 代理费用降低 42%。
3. **业务支撑：** 成功支撑 8 月 Marketplace Insights 平台顺利上线。
4. **可迁移经验：** 增量更新 + 缓存分层已复用到价格监控链路，说明这是一套可复用的架构范式，而非一次性优化。

---

### 本例的可复用点

- **行动写动作，不写决心：** “引入异步无头浏览器集群”是动作，“我高度重视、全力推进”是态度。评审只能为动作打分。
- **结果必须带锚点：** “提升 650%”本身不构成结论，配上“Q2 基线 20 万”和“部门目标 +200%”才有判断依据（这正是 Data-In-Context 的作用）。
- **多讲一条可迁移性：** 晋升评审的核心疑问是“他能不能做更大的事”，所以 R 里要有一条说明能力可复用的证据。
- **S/T 可以合并成一段**，但 A 和 R 必须分开：读者要能一眼看出“哪些是我做的”和“做成了什么”。
