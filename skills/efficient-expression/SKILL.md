# Efficient Expression（高效表达框架）

表达的失败通常不是文笔问题，而是三层中的某一层塌了：事实是糊的（说不清发生了什么），逻辑是散的（听的人不知道要干嘛），语言是错位的（用技术黑话讲给业务方听）。这个 Skill 把表达拆成三层，按场景只加载需要的那一层，让每一次输出都在“事实精准、逻辑顺畅、语言适配”上闭环。

核心原则：**先确定对谁说、要他做什么，再决定怎么说。** 没有场景判断就开始写，是这套流程最常见的失败方式。

## 执行流程（Pipeline Orchestration）

```text
[用户输入 / 原始诉求]
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│ Step 0：事实完成度检查（Fact-Check Protocol）              │
│ ├─ 事实完整？        ──► 直接推进到 Step 1                 │
│ ├─ 公域知识缺失？    ──► 触发 Deep Research 自动检索补齐    │
│ └─ 私域/内部背景缺失？──► 触发 HITL 主动追问（≤3 个问题）   │
└──────────────────────────┬───────────────────────────────┘
                           │ 得到完整事实
                           ▼
┌──────────────────────────────────────────────────────────┐
│ SOP 选择与动态裁剪（SOP Execution Engine）                 │
│ 按【场景决策矩阵】确定各层方法，或明确跳过某一层            │
│ ├─ Step 1：事实清洗层（5W1H / IPO / Metric-Variance ...）  │
│ ├─ Step 2：叙事框架层（SCQA / PROACT / STAR / ...）        │
│ └─ Step 3：语言渲染层（BLUF / KISS / ELI5 / NVC / ...）    │
└──────────────────────────┬───────────────────────────────┘
                           │ 组装与渲染
                           ▼
                    [最终表达输出]
```

## 场景决策矩阵（Scenario Decision Matrix）

处理任何表达任务前，**先确定“业务场景 / 行业”**，再由场景激活对应的 SOP 策略与参考文档。场景判断错误，后面三层全都白做。

| 业务场景 / 行业 | 核心表达目标 | Step 1（事实层） | Step 2（叙事层） | Step 3（渲染层） | 关联参考 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **高管汇报 / 决策请示** | 极速决策、划拨资源 | Metric-Variance / 5W2H | **PROACT**（决策对比） | **BLUF + KISS** | `references/step2-narrative.md`、`references/step3-rendering.md`、`examples/01-executive-reporting.md` |
| **技术架构 / 方案选型** | 说明合理性、澄清影响 | **IPO**（输入/逻辑/输出） | **PROACT** 或 SCQA | **KISS**（保留专业术语） | `references/step1-fact-layer.md`、`examples/01-executive-reporting.md` |
| **产品发布 / 品牌宣讲** | 唤起共鸣、用户转化 | 4P/4C / 5W1H | **Golden Circle**（Why） | **ELI5**（类比降维） | `examples/02-product-pr-launch.md` |
| **案例复盘 / 绩效谈话** | 证明能力、总结经验 | Metric-Variance / 5W1H | **STAR**（行为闭环） | **Data-In-Context** | `references/step2-narrative.md`、`examples/04-performance-review.md` |
| **知识分享 / 技术培训** | 降维吸收、建构认知 | IPO / 概念映射 | **ADEPT**（教学引导） | **ELI5 + KISS**（分段切换） | `references/step2-narrative.md`、`examples/05-tech-sharing-training.md` |
| **部门协同 / 冲突缓解** | 消除对抗、达成共识 | 5W1H（只留客观事实） | **SCQA**（共同问题） | **NVC**（同理心渲染） | `examples/03-cross-team-conflict.md` |
| **线上事故 / 故障通告** | 交代影响、恢复信任 | 5W1H + Metric-Variance | **SCQA**（压缩形态） | **BLUF + Data-In-Context** | `references/step0-fact-check.md`、`examples/06-incident-postmortem.md` |

场景跨类别时，按“谁做决定、谁受影响”拆分：给决策者的一段走 PROACT + BLUF，给执行者的一段走 SCQA + KISS，而不是让一段文字同时承担两种目标。

### Step 1→2→3 是加工顺序，不是排版顺序

当 Step 3 选定 **BLUF**（高管汇报、故障通告）时，结论会被物理提到最前面，Step 2 的叙事骨架从第二段才开始。案例 1（BLUF 在 PROACT 表之前）与案例 6（BLUF 在 SCQA 之前）都是这个形态。看到这种情况不要去“修正”顺序——它正是裁剪规则在生效。

### 案例库使用规则（`examples/`）

`examples/` 下有六个完整案例，与上表的「关联参考」列一一对应。它们的用途是**示范路径怎么走**，不是复制内容：

- **借骨架：** 段落顺序、对比表的维度、锚点的写法、改进措施的字段——这些直接复用。
- **不借事实：** 案例里的事故时长、指标数字、公司名与产品名（Nexus、LangChain、150 万商品）都是示例语境，搬进真实输出就是编造。用户没给的数据，走 Step 0 去补。

## 动态裁剪规则（Dynamic Bypassing Rules）

三层 SOP **不是每次都全跑**。硬套三层会把一条钉钉消息写成一封汇报信，这也是失败。处理时遵守：

1. **跳过 Step 1（事实清洗）：** 若原始信息本身已经结构化（监控日志、已导出的报表、已有的接口文档），直接进入 Step 2 —— 再“清洗”只是重复劳动。
2. **跳过 Step 2（叙事框架）：** 即时通讯（Slack / 钉钉 / 企微）上的极简问答、状态更新、确认类消息，不需要铺陈故事骨架，直接到 Step 3 用 BLUF / KISS 输出。
3. **保留 Step 3（语言渲染）：** **Step 3 为强制层。** 无论前面怎么裁剪，输出都必须匹配受众的“接口协议”（认知背景 + 精力成本）。受众读不懂，等于没表达。

## 输出格式（Output Format）

默认按场景组织正文；当 Step 2 有明确框架时，用标题把框架显性化，让读者沿骨架阅读，例如：

```markdown
【结论与请求】        # BLUF：第 1 句给结论与诉求
【决策权衡对比】      # Step 2 框架主体（PROACT / SCQA / STAR ...）
【下一步计划】        # 明确的行动项、负责人、时间点
```

读者是需要转发的人（秘书、领导、客户）时，保持标题显性；读者是同级、只需要一个答案时，可以去掉标题，用 3 行以内说完。

若用户明确要求，或本次裁剪路径不直观（跳过了某一层、临时改用了别的框架），在正文后附加一段简短的 **「表达设计思路」**：说明选了哪个场景、哪几层、为什么。默认不加，避免喧宾夺主。

## 执行步骤与指令规范

1. **Step 0 — 校验事实：** 读取 `references/step0-fact-check.md`。事实达标则继续；不达标则先补齐：公域知识走 Deep Research（自动检索并标注来源），私域背景走 HITL（暂停生成，提出 ≤3 个定量问题并等待回答）。
2. **场景匹配：** 对照【场景决策矩阵】确定业务场景；无法确定且影响输出时，用一句话向用户确认受众与目标，而不是猜。
3. **加载模块：** 按矩阵读取 `references/` 下对应子文档；需要范例时读 `examples/` 下的案例，**借其骨架，不借其事实**。
4. **生成输出：** 按 Step 1 → Step 2 → Step 3 的顺序组装（被裁剪的层跳过），用上面约定的格式交付。

## 反模式（Anti-patterns）

- **信息不足硬编：** 缺数据时用“大幅提升”“明显改善”填坑。宁可 HITL 追问一次，也不要输出一段无法被采信的汇报。
- **框架堆叠：** 一份输出里同时上 PROACT 和 SCQA、再套 ELI5。一个受众、一个目标、一个主框架。
- **对错位受众渲染：** 给高管写 ADEPT 教学长文，或给一线工程师写营销式 Golden Circle。Step 3 的判断依据是受众的认知背景与精力成本，不是作者的表达欲。
- **讨好式汇报：** 只报结论、回避风险与备选方案。PROACT 里的 Consequences & Trade-offs 是汇报可信度的来源，不能省。
- **照抄案例：** 把 `examples/` 里的公司名、指标数字、产品名搬进用户的实际输出。案例只示范路径，不提供事实。
